## Change intent: what it changes about your review

This repository uses change intents. Every pull request carries one current intent file at `change-intent/YYYY-MM-DD-short-slug.md`; its initial candidate was approved before implementation began, and the author may have replaced an unmerged candidate before the current implementation and review pass. Treat the current intent as complete over change-defining decisions and open over implementation. Assess whether the diff satisfies its claims, honors its decisions, and makes any unrecorded change-defining decision. Do not require the intent to enumerate every technical choice, incidental effect, invariant location, or invariant test. If a pull request has no intent file, perform the normal review and raise a finding for the missing intent.

Review the implementation and its evidence independently. The implementation agent proved its tests through semantic would-fail demonstrations in its own session, but your review does not depend on receiving that context. Use the evidence and capabilities available in your team's review operation, together with inference, to assess each acceptance criterion's proving test and each invariant across the affected change. Report the limits of what you can establish. If no finding remains, report what you established and how; do not issue a bare approval.

### The intent file, from the review seat

- **Outcomes** — the results the author wanted. Not verified at review; your judgment call is whether the claims below plausibly deliver them.
- **Why** — the problem, event, or need that caused the change. It explains why the work exists; it is not a checklist, requirement, or source of implementation direction.
- **Constraints** — conditions and non-behavioral boundaries every acceptable implementation must be designed around. Use them as lenses for engineering judgment. Do not require a test or conclusive verdict for each constraint, and do not treat unavailable production proof as a violation. Raise a finding when the diff affirmatively conflicts with a constraint or is materially implausible under it; state uncertainty when it matters.
- **Acceptance criteria** — falsifiable scenarios. For each criterion, assess its proving test and the relevant implementation using the evidence and review mechanics available to you. Mark it `met` when the evidence shows the test passes and its assertions would detect the criterion's defining condition becoming false. Mark it `not met` when the evidence establishes a mismatch. Mark it `cannot verify` when the available evidence does not support either conclusion. State the basis for every assessment. The implementation agent's semantic would-fail demonstration may support the assessment when available, but it is not a required review input.
- **Invariants** — properties that must remain true across the parts of the system affected by the change. Tests may establish concrete cases but no passing test closes an invariant by itself. Use available tests and reason across the affected diff and relevant surrounding paths. Record `met`, `not met`, or `cannot verify` for every invariant and state the basis. The intent states the property, not a site or test inventory; if your process provides the implementation agent's analysis, treat it as supporting context rather than a prerequisite.
- **Out of scope** — decisions, not oversights. Never flag a listed item as missing work. An exclusion waives missing work only: a defect in code this change ships — a security hole, a correctness bug — is a finding no matter what list its subject appears on.
- **Amendments** — a short history of eligible implementation repairs to the current approved baseline. Read the body first; it must completely describe the current intent without amendment markers or history. Then assess amendment eligibility: the discovered fact must show that the pre-amendment `Was` claim could not be delivered within the approved outcomes, constraints, and exclusions, or that implementation could not complete without deciding which change would be delivered. A limitation of the chosen approach is not enough when a plausible alternative supported by the repository and normal scope can satisfy the approved intent. Inability to prove a constraint is not eligible. Check coherence using the entry itself: `Was` names the previous section and quotes the complete prior item verbatim; `Now` names the current section and quotes the complete current item verbatim, or the entry explicitly records addition or removal. For repeated changes, one entry's `Now` equals the next entry's `Was`, and only the terminal `Now` must match the current body. A relaxed claim records an Out of scope deferral only when the prior strength is actually deferred. For a missing-decision amendment, also assess whether implementation applied the shared precedence and recorded either the selecting rule or a full tie. Do not reconstruct Git history to authenticate `Was`.

### Rules that follow

- **Run the decision check in both directions.** Forward: assess the implementation and evidence for every claim, then assess whether the diff accounts for each recorded decision and constraint without demanding unavailable proof. Reverse: inspect the change for a choice that decided which change would be delivered when the approved intent did not make that choice. Ask whether the author could have approved the change once and allowed either reasonable branch while still receiving the approved change. If yes, classify it as implementation latitude. If choosing one branch would make the other a different change, raise a finding for the unsettled decision. This is a diligent bounded discovery pass, not proof that no unknown dependency exists; report `cannot verify` when a relevant surface cannot be assessed.
- **Do not promote incidental effects into intent defects.** Query count, latency, retries, caching, logging, metrics, abstractions, operational risk, or cost can be serious ordinary-review concerns. They become intent-alignment concerns only when this intent or an explicit constraint made them change-defining.
- **Keep ordinary review and intent-alignment review as distinct judgments, regardless of input order.** Review correctness, security, concurrency, error handling, and other defects whether or not the intent mentions them. Use the intent to assess the approved change; do not use its silence, exclusions, or decisions to excuse a defect in code the pull request ships. If a recorded decision is itself unsafe or incorrect, raise the finding against the intent.
- **Check the intent as well as the code.** A claim that is too vague to evaluate is a blocking finding regardless of the implementation. Review cannot verify alignment against an indeterminate decision record.
- **Keep the assessment scoped to this change.** Use this pull request's intent. Do not search earlier intent files for decisions this change must preserve or explain, and do not compare against intents on other branches. The current intent describes this pull request, nothing more.
- **Check only the current intent file.** The pull request carries exactly one current intent for this change. Implementation amendments appear in that file. An author replacement supersedes the prior unmerged candidate and starts a clean baseline, so review does not reconstruct, compare, or assess prior candidates or their amendment history. Assess the current intent and current change together.
- **Your existing review still runs in full.** Security, concurrency, error handling, clarity — everything you check today, you keep checking. The intent tells you where to look harder; it never shrinks the job. If the change is too large to perform both judgments well, say so — a change too large to review against its claims is itself a finding. Report `cannot verify` for an intent claim you cannot assess; do not narrow ordinary review to manufacture complete intent-alignment results.
- **Report; do not repair.** `Not met`, an unrecorded change-defining decision, or an ineligible or incoherent amendment is a finding. If the available intent, diff, tests, or repository cannot establish a conclusion, report `cannot verify`. `Cannot verify` does not establish that the claim is met. State what the available inputs could not establish, then continue and complete the review. Review never invents a claim or amendment to make the change pass.
