# Tasks

A task is one exercise: a seed repository, a brief, hidden tests and a reference solution, packaged
as a [Harbor](https://github.com/harbor-framework/harbor) task directory. Every process version runs
against every task with the same driver, reviewer and grader; what differs between tasks is written
down in one file, `tests/task_config.json`. All three tasks are Python and pure standard library.

| Task | Type | The agent is asked to | Seed | Hidden tests (seed / reference) |
| --- | --- | --- | --- | --- |
| [`ledger-budgets`](ledger-budgets/instruction.md) | extension | add budgets, recurring transactions, bank-CSV import and a report to a 300-line CLI, under a precise interface contract | the `ledger` CLI and its 17 tests | 5 / 37 of 37, in-process via `ledger.cli.main` |
| [`cloudbill-report`](cloudbill-report/instruction.md) | greenfield | build `cloudbill`, a streaming CLI answering eight cost-review questions in three formats over a messy cloud billing export, from a ticket that leaves encodings, duplicates, rounding, the percentile method and the text layout to the implementer | README, `pyproject.toml`, `CHANGELOG.md`, a 3,575-row sample export in two files; no code, no tests | 0 / 55 of 55, black box (`python -m cloudbill` in a subprocess), including a peak-memory test on a 1,500,000-row export |
| [`cloudbill-sqlite`](cloudbill-sqlite/instruction.md) | migration | move every answer onto SQLite: idempotent `load`, restatements across loads, provenance, a `files` listing, `schema.sql`, byte-identical output from files and from the database | `cloudbill-report`'s reference solution (about 1,160 lines with 54 tests) | 2 / 75 of 75, black box: the report task's 55 asked of a database loaded from the files, plus 20 database tests |

Seed / reference is hidden tests passing on the untouched seed and on the reference solution. The two
cloudbill-sqlite tests the seed passes are an exit-code check and the file-mode memory test, which the
seed satisfies by construction.

## cloudbill-report

The brief is a ticket from a colleague in platform finance who spends two days a month in a
spreadsheet and got one comparison badly wrong last quarter. It names the questions (`costs`, `daily`,
`top`, `untagged`, `credits`, `mom`, `daily-stats`, `rejects`), the options (`--from`, `--to`,
`--format text|json|csv`), the JSON field names, the rules finance agreed (UTC usage day, what counts
as a charge or a credit, accounts are ids, services are case-insensitive, blank or absent tags are
untagged, the later restatement wins, only USD), what makes a row unusable, the exit codes, and two
hard constraints: stdlib only, and peak memory under 100 MB however big the export (the full export is
about 2 GB). It does not say how to handle encodings, how to resolve duplicates beyond restatements,
how to round, how to compute a percentile, or what text output looks like; it asks for those decisions
in the README.

The data is generated by `tests/__hidden/billing_gen.py` (seeded, deterministic, never in the seed).
The sample in the seed, which the build script writes from the same generator, carries every edge case
the hidden tests use without listing any of them: credits and refunds as negative lines, restatements
within a file and across files, a partial month, a UTF-8 byte-order mark and CRLF line endings on one
file, descriptions with embedded commas, quotes and line breaks, rows with too many or too few fields
(one a truncated last line), a cost of `#VALUE!`, a blank tag versus a missing tag column, one account
whose costs carry thousands separators, the same service spelled three ways, trailing whitespace, a
zero-cost line, a non-USD line, an account renamed mid-month, account ids with a leading zero, a local
time column that disagrees with the UTC day, and the two files' columns in different orders.

The hidden tests check only what the brief states, plus properties: byte-identical output across two
runs, groups that add up to the total, charges plus credits equal to net, credits and untagged figures
that agree with the per-account view, the rejected count in every output and format, CSV carrying the
JSON fields, and answers independent of file order. Expected values come from the generator's own
records (an oracle in `billing_gen.py`), never from parsing the CSV. Money is compared to the cent, so
any consistent rounding passes. Where the brief leaves a choice (the percentile method, missing months
in `mom`, rows for groups with no value), the tests accept every reasonable answer. To keep any one
property from dominating the pass fraction, determinism is one test, the rejected count is three (one
per format) and CSV mirroring is one.

The memory test runs the tool as the only child of a small measuring process and reads `ru_maxrss`
from `RUSAGE_CHILDREN`, with one run of the tool capped at 240 s so a slow tool fails this test and
not the suite. On the 1,500,000-row export (about 380 MB, written in about 10 s) the reference peaks
at about 36 MB in 29 s (`load` 27 MB in 32 s, a question from the database 25 MB in 13 s). Every
design that keeps something per line item id fails the 100 MB cap by a wide margin: a bare set of
ids 183 MB, an int per id 195 MB, an id-to-`last_updated` map 270 MB, an id-to-(`last_updated`,
cost) map 419 MB; loading the file costs gigabytes. (At 600,000 rows, the earlier size, the
id-to-`last_updated` map measured 98 MB, a knife edge the fifth review pass removed.) The reference
resolves restatements in two passes, spilling sorted runs of hashed line item ids to disk so that
memory grows with the number of restated items, not with the export. Plausible mistakes score
partially rather than all or nothing (hidden tests failed, of 54 without the memory test): taking the day from the local column 22, ignoring restatements 18, rejecting thousands
separators 23, parsing account ids as integers 9, case-sensitive services 5, counting records instead of
physical lines in `rejects` 2.

## cloudbill-sqlite

The seed is cloudbill-report's reference, laid over cloudbill-report's seed by `scripts/build_tasks.py`
and never edited by hand; its 54 tests are the seed tests the grader keeps passing (`tests/__seed`).
The brief asks for `load --db PATH FILE...` (idempotent by content, restatements across loads, a failed
load loads nothing), `files --db PATH` with `path`, `sha256`, `loaded_at`, `rows`, `rejected`, `--db
PATH` on every question with byte-identical output, exit 1 for a missing or foreign database, a single
`schema.sql` that builds a working database, the existing tests still passing, and the same 100 MB
memory limit for loading and querying.

The hidden suite is cloudbill-report's, copied in by the build script, and this task's config sets
`"hidden_answers_from": "database"`: the shared conftest then answers every question by loading the
question's files into a fresh database and asking with `--db`. So the reused suite is the database's
correctness oracle (a workspace without a working `load` fails all of it), and `test_database.py` adds
what is new: byte-identical answers from files and from the database for every question and format,
the schema file applied to an empty database (and covering every table the tool itself creates),
loading twice and loading a renamed copy leaving the database dump unchanged, an incremental second
month, a restatement across files loaded in either order, the provenance listing, a failed load leaving
the dump unchanged, database errors, and loading and querying the 1,500,000-row export under the cap.

The reference overlay (`solution/repo`) adds `db.py` and `schema.sql` and replaces `cli.py`,
`render.py`, the README, the CHANGELOG and `pyproject.toml`; file mode loads the files into a temporary
on-disk database, so the two paths agree by construction. `solution/BASE.sha256` records the hashes of
the seed files the overlay replaces; if cloudbill-report's reference changes under them, the build
check fails until the change is ported and `scripts/build_tasks.py --accept-base` is run.

## task_config.json

Read by the driver (Harbor uploads it next to the driver as `/eval/task_config.json`; `run_local.sh`
puts it in the same place in its private harness copy; it never enters the workspace) and by the
grader (from the task's `tests/`, which is all Harbor copies at verification time). It is JSON rather
than TOML because Reward Kit parses every `.toml` at the root of a criteria directory.

| Key | Read by | Meaning |
| --- | --- | --- |
| `name`, `type`, `language` | both, analyzer | the task (recorded in `summary.json` and in the analyzer's condition key); `extension`, `greenfield` or `migration`; `python` |
| `package` | grader, hidden tests | the importable package; counts as first-party for the stdlib check; the cloudbill hidden tests run `python -m <package>` |
| `code_dirs` | both | where the implementation lives: the continuation rule counts a change only under these (`ledger/`, so `./ledger.csv` is not code), and the stdlib check parses only these |
| `visible_test_command` | both | `python -m pytest ...`: the driver's "visible suite green" check (an empty suite is not green) and the grader's `agent_tests_pass` |
| `seed_tests`, `seed_test_count` | grader | the seed's own test files and how many tests they hold; pristine copies live in `tests/__seed` (every `.py` there is staged, so a seed `conftest.py` travels with its tests). Empty for greenfield, and then `correctness/regression.py` does not register the seed-regression criterion at all |
| `hidden_timeout_sec` | grader | the time box for one pytest run (keep `task.toml`'s verifier timeout above it) |
| `fake_reference` | `run_local.sh`, build guard | the directory the fake backend copies in as "the implementation", relative to the task |
| `hidden_answers_from` | cloudbill hidden conftest | `database` makes the shared cloudbill suite answer through `load` and `--db` |
| `build` | `scripts/build_tasks.py` | files this task derives from another task or a generator (below) |

## Generated files

`scripts/build_tasks.py` is the only writer of these, and `scripts/build_tasks.py --check` (run by
`scripts/test_build_tasks.py`) fails when any of them is stale or hand-edited:

- in every task, `tests/criteria.py`, `tests/reward.toml`, `tests/test.sh` and the criteria groups
  `tests/{correctness,review,handoff,diagnostics}/`, mirrored from `eval/grading/`. Edit the source
  there; task-specific settings go in `task_config.json`, never in these files;
- `cloudbill-report/environment/seed/sample/`, from `tests/__hidden/billing_gen.py sample`;
- `cloudbill-sqlite/environment/seed/` (the report task's seed plus its reference solution),
  `cloudbill-sqlite/tests/__seed/` (the reference's tests, conftest included) and the report task's
  hidden files in `cloudbill-sqlite/tests/__hidden/` (a mirror that keeps this task's own
  `test_database.py`, so a file removed from the report task's suite disappears here too);
- `cloudbill-sqlite/solution/BASE.sha256`, the overlay guard described above. It is written when
  missing and only rewritten by `--accept-base`.

Build steps are declared in `task_config.json` and run in dependency order:
`{"copy": "<task>/<path>", "to": "<path>", "mode": "mirror"|"overlay", "keep": [...]}` or
`{"generate": "<script in this task>", "args": [...], "to": "<path>"}`.

Stray caches are prevented rather than cleaned: every task has an `environment/.dockerignore`,
`run_local.sh` copies the seed with tar excludes, and `test_no_caches_in_any_seed` fails if a seed
holds `.pytest_cache` or `__pycache__`.

## Adding a task

1. Create `tasks/<name>/` with `instruction.md`, `task.toml`, `environment/Dockerfile` (copy one;
   it only needs Python, git, pytest and uv), `environment/.dockerignore`, `environment/seed/`,
   `solution/solve.sh` plus the reference files, and `tests/__hidden/` with a `conftest.py` that
   finds the workspace through `EVAL_WORKSPACE` and gives every test a time limit. Nothing in the
   seed may name the experiment (`test_seeds_never_name_the_experiment`).
2. Write `tests/task_config.json` (table above). For a task derived from another, add `build` steps
   rather than copying files by hand.
3. Run `scripts/build_tasks.py` to write the shared grading code (and anything derived), then
   `python -m pytest scripts/test_build_tasks.py -q`.
4. Check the task: the hidden tests against the seed (nearly all should fail) and against the
   reference (all must pass), with `EVAL_WORKSPACE=<dir> python -m pytest tests/__hidden -q`; then
   `scripts/run_local.sh <name> baseline --backend fake` must grade correctness 1.0.
5. Add a line to the table above. Nothing in the driver, the agent classes or the analyzer changes:
   the Harbor agent finds the task from the instruction it is given, and the analyzer keys
   conditions by task.

Hidden tests live under `tests/__hidden/` because Reward Kit imports every `.py` under a criteria
directory and skips directories whose names start with `__` or `.`; Harbor copies `tests/` into the
container only at verification time, so the agent never sees them.

## Merge decisions

Two implementers built this scope independently; one unified change was assembled from the two. The
base for each piece, and why:

- **Harness contract: the second implementation.** Its `task_config.json` is JSON because Reward Kit
  loads every `.toml` at the root of a criteria directory (`_load_directory_tomls`), so a TOML config
  there is one unlucky key away from being parsed as a judge; JSON is never looked at. Its build
  script is declarative (`build` steps in the config, topological order, `--check` by building into a
  temporary copy and diffing), which is what "how to add a task" needs; the first implementation's
  script hard-wired the two cloudbill tasks. Its `correctness/regression.py` leaves the
  seed-regression criterion absent on a greenfield task instead of a free weight-2 `true`. Its
  `agents/task_select.py` matches a task by containment (Harbor may append to an instruction) with no
  Harbor import, so it is tested offline. Its `.dockerignore`, tar excludes and no-caches test prevent
  the stray-cache problem instead of cleaning it once.
- **Grafted from the first implementation into that harness:** the overlay base guard
  (`solution/BASE.sha256`, `--accept-base`), made generic (any task whose seed is built from another
  task and whose reference replaces seed files); the staging of every `.py` under `tests/__seed`, so a
  seed `conftest.py` travels with its tests; the fake backend creating `tests/` for a greenfield seed;
  the seed-wording test; the `keep` option on a mirror step, so the migration task's hidden directory
  cannot accumulate files the report task deleted.
- **Tasks A and B: the first implementation (cloudbill).** Its brief is a ticket with a reason and a
  story (the half-September comparison), leaves the percentile method, the text layout and the
  rejected-count placement open, and states the memory bound the way the user asked for it (2 GB on
  a laptop, 100 MB peak). Its reference actually meets that bound: restatements are resolved with
  sorted runs of hashed ids spilled to disk, so memory grows with the number of restated items, not
  with the export; the second implementation's reference keeps one integer per line item id, which
  passes its own 50 MB yardstick but would not pass at 2 GB. Its memory test uses a large export
  (600,000 rows at the merge, 1,500,000 since the fifth review pass) rather than a 50 MB one, its oracle covers every question from the
  generator's records, and its test counts are balanced so no single property dominates the pass
  fraction. Both reference solutions sit in the 900 to 1,500 line target; both sets of hidden tests
  fail on the seed and pass on the reference.
- **Grafted from the second implementation into those tasks:** idempotency by content is stated in
  the brief ("a file whose contents are already loaded is skipped, whatever its name") and tested
  with a renamed copy and a database dump comparison; the schema test also checks that `schema.sql`
  covers every table the tool creates itself; a failed load is checked to leave the dump unchanged.
  Its `oracle_mode.py` hook was not taken: the first implementation's `hidden_answers_from` config
  key does the same job with one copied conftest and no module-presence magic, and a workspace
  without `load` fails every reused test either way.
- **Not taken from either:** the second implementation's stated nearest-rank percentile (the brief
  should leave that decision open), its CSV trailing comment line as a stated requirement, and its
  three-file sample (two files, one complete and one partial, carry the same edge cases).
- **Found while merging:** the fake backend copied the reference with `shutil.copy2`, which keeps the
  source mtime. A replaced seed file of the same size and second-stamp (`pyproject.toml`) was then
  invisible to `git add -A`, so the implementation commit lacked it and the tree only showed dirty
  after the run directory was copied. It now copies with a fresh mtime, as an agent's edit would.
